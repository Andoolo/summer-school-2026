# Описание домена и ограничения

> **Этап 1. Артефакт 1 проекта:** согласованное описание домена + список ограничений.
> Заполняется после ответов заказчика ([customer-questions.md](customer-questions.md)).

## Описание домена

**Бизнес.** «Апекс» — уличный картинг-центр на окраине города, работающий третий год. Центр
организует **групповые заезды** на картах по трассе. Один заезд длится ~15–20 минут плюс
предстартовый инструктаж (брифинг), который проводит маршал и который входит в слот. Заезд
проходит по одной из **конфигураций трассы**: короткая — попроще для новичков (с картами
ограниченной скорости), длинная — для опытных. Каждый заезд ведёт **маршал-инструктор**
(сейчас их пятеро, летом нанимаются подработчики).

**Процесс.** Владелец заранее формирует **расписание на неделю вперёд**: для каждого заезда
задаются дата и время старта, конфигурация трассы, назначенный маршал и число мест. Центр
располагает **14 картами**; для новичковых заездов берут не более 8 человек (тяжелее уследить,
часть картов с ограничением скорости), для опытных — до 14 (по числу картов). **Карт всегда
выдаётся центром** — у клиента нет «своего карта»; одно место = один карт. Клиент видит
свободные **слоты** заездов и **записывается**, указывая, поедет он со своей экипировкой
(шлем + подшлемник) или возьмёт её **напрокат**. До заезда клиент может **отменить** запись —
при ранней отмене место-карт освобождается, поздняя отмена оставляет карт простаивать. Сейчас
запись клиентов ведётся вручную (Telegram + доска маркером), что приводит к двойным записям и
путанице, особенно в выходные.

**Цель клиентского приложения.** Дать клиентам самостоятельную онлайн-запись на заезды (просмотр
и фильтрация слотов, бронирование, выбор экипировки, отмена, свои бронирования), исключив ручную
путаницу и двойные брони. Управление расписанием и работу маршалов/владельца обеспечивает
**существующая инфраструктура**; приложение потребляет её данные через API.

**Ключевые объекты домена:**

- **Заезд / слот** — конкретный выезд группы: дата/время старта, конфигурация трассы, маршал,
  всего и свободно мест-картов. Создаётся в существующей инфраструктуре; клиенту доступен только
  для чтения.
- **Конфигурация трассы** — вариант заезда (новичковая / опытная), определяет длительность и
  потолок мест (справочные данные, read-only).
- **Маршал** — ведёт заезд, проводит инструктаж, следит за трассой; для клиента — справочные
  данные слота (read-only).
- **Карт** — инвентарь (всего 14); всегда выдаётся центром, не имеет варианта «свой».
- **Экипировка (прокатный комплект)** — шлем + подшлемник; может выдаваться напрокат. Подшлемник
  — предмет личной гигиены, при прокате выдаётся новым (индивидуальный).
- **Запись (бронь)** — резерв места-карта клиентом на конкретный слот: число мест, своя/прокатная
  экипировка, статус.
- **Клиент** — записывается на заезды, отменяет запись.

> **Ключевое доменное отличие (картинг).** В отличие от сервисов, где «своя/прокатная» относится
> к основному инвентарю (доска, велосипед), в картинге **карт всегда центра**, а выбор
> «своя/прокатная» относится **только к экипировке** (шлем + подшлемник). Поэтому:
> - **Места-карты** = основной лимит заезда (`free_seats`).
> - **Прокатная экипировка** = отдельный независимый лимит (`free_rental_kits`).
> - «Своя экипировка» занимает место-карт, но **не** занимает прокатный комплект.

## Пользователи и роли

> **Скоуп текущей работы — только клиентское мобильное приложение и API для него.**
> Роли Маршал и Владелец/Администратор обслуживаются **существующей инфраструктурой**
> (бэкенд, расписание, админка) и в этот скоуп не входят.

| Роль | Описание | Цели | В скоупе |
| :-- | :-- | :-- | :-- |
| **Клиент** | Гость центра, катается на картах. Пользуется с телефона. | Увидеть и отфильтровать свободные слоты, записаться (себя и гостей), выбрать свою/прокатную экипировку, видеть свои бронирования, отменить запись, получать напоминания. | **Да** |

> Маршал и Владелец/Администратор взаимодействуют с системой через **уже реализованные**
> интерфейсы существующей инфраструктуры. Клиентское приложение лишь потребляет подготовленные
> ими данные (слоты, конфигурации, маршалы) через API.

## Ограничения

**Бизнес-ограничения**

- Всего **14 картов** — потолок мест-картов заезда и прокатного фонда экипировки (по числу мест).
- Новичковый заезд — **не более 8 человек**; опытный — до 14 (по числу картов).
- Лимит мест слота = `min(свободные карты, потолок конфигурации)`.
- **Политика отмен:** бесплатная отмена не позднее чем за **2 часа** до старта; поздняя отмена
  (<2 ч) фиксируется без освобождения места-карта и без денежных штрафов.
- **Оплата офлайн** (наличные / перевод на карту) — приложение лишь фиксирует запись и показывает
  цену.
- **Период списка слотов по умолчанию — 7 дней (R-027).** По умолчанию клиенту показываются слоты
  на **ближайшие 7 дней** от текущего момента — это совпадает с горизонтом планирования расписания
  («на неделю вперёд»). Более длинный период доступен через **фильтр дат**. При отсутствии
  расписания на ближайшие дни показывается **empty state** («Пока нет доступных заездов»).
- **Отмена заезда центром / по погоде (R-008).** Если заезд отменяет центр (организатор или из-за
  погоды — дождь, гололёд), бронь на стороне клиента **не удаляется**, а получает статус
  **«Отменён центром»** с указанием причины; клиенту приходит **push-уведомление**. **Повторная
  запись на отменённый слот запрещена.** Само действие отмены слота выполняется в существующей
  инфраструктуре (вне скоупа клиентского приложения).

**Технические / платформенные**

- **Правило работы со временем (R-021).** Время хранится и передаётся в API в **UTC**. Различаются
  две зоны ответственности:
  - **Бизнес-правила** (граница ранней/поздней отмены 2 ч, окно выдачи списка слотов, SLA
    доступности) считаются в **локальной зоне центра** (для уличного картинга — единая зона места
    проведения). Источник истины по времени и по статусу отмены — **сервер**.
  - **Отображение пользователю** (дата/время старта в карточке и списке) — в **локальной зоне
    устройства клиента**. При расхождении клиентского прогноза и серверного ответа применяется
    **серверный** статус.
- **Mobile-first**: клиентское приложение рассчитано на телефон (использование у трассы).
- Клиентское приложение взаимодействует с **существующим бэкендом через API**; слоты, конфигурации
  и маршалы доступны только для чтения.
- **Граница серверной интеграции (R-004).** Детали серверной реализации — транзакционность, SLA,
  маппинг сущностей на внутренние модели бэкенда — **вне скоупа клиентского приложения**.
  Существующий бэкенд — **black-box источник истины**: гарантия «**0 двойных броней**»
  обеспечивается на его стороне (атомарная проверка свободных картов при бронировании). Со стороны
  клиента граница закрывается **контрактом API**: приложение полагается на ответы бэкенда и
  корректно обрабатывает отказ, если мест уже нет.
- **Данные существующей инфраструктуры (R-015).** Это **учебный/тестовый проект**, исторических
  данных и легаси-схемы нет. **Канонической схемой считается контракт API** (OpenAPI в
  `01-analysis/api/`): бэкенд по условию отдаёт ровно те поля, что описаны в контракте, включая
  `rental_price`, `geometry`, `meeting_point` и `free_rental_kits`. Поэтому **миграция/backfill и
  стратегия дозаполнения исторических слотов вне скоупа** — отдельных требований к ним не
  формулируем.

**Проект**

- **Срок** — к старту высокого сезона, ~2 месяца (жёсткая цель).
- **Бюджет** ограничен → начинаем с самого нужного, «навороты» позже.

**Границы скоупа**

Скоуп — **клиентское мобильное приложение и API для него**. Управление расписанием, роли маршала
и владельца, оценки, админка — это **существующая инфраструктура**, вне скоупа.

| В скоупе клиентского приложения | Вне скоупа (существующая инфраструктура / не делаем сейчас) |
| :-- | :-- |
| Регистрация/вход клиента по имени и телефону | Роли Маршала и Владельца/Администратора, админ-экран |
| Просмотр и **фильтрация** списка слотов (дата, тип конфигурации, наличие мест, маршал) | Создание и редактирование расписания (слоты приходят из существующего бэкенда через API) |
| Самостоятельная запись, в т.ч. несколько мест за раз | Оценка маршала и рейтинги — **Phase 2** (R-001; заказчик ранее называл функцию критичной, перенос в Phase 2 согласован с заказчиком 2026-06-30) |
| Выбор «своя / прокатная экипировка», контроль лимита мест-картов и прокатного фонда | Отметка явки/неявки, отмена слота маршалом + массовое уведомление |
| Список своих бронирований | Онлайн-оплата; ручная отметка «оплачено» |
| Отмена записи с правилом 2 часов | Автоматический учёт погоды по прогнозу |
| Цена и фиксация записи (оплата офлайн) | Программа лояльности для постоянных клиентов; подбор карта под рост/возраст |
| Напоминания о записи — по возможности в срок | Публичный показ рейтинга клиентам — **Phase 2** (R-001) |

## Глоссарий

| Термин | Определение |
| :-- | :-- |
| **Заезд / слот** | Запланированный групповой выезд: дата/время старта, конфигурация трассы, маршал, всего и свободно мест-картов. |
| **Конфигурация трассы** | Вариант заезда: новичковая (короткая, потолок 8, карты с ограничением скорости) или опытная (длинная, до 14). |
| **Группа** | Состав клиентов, записанных на один слот. |
| **Карт** | Картинг-мобиль из инвентаря центра; всего 14; всегда выдаётся центром (варианта «свой карт» нет). |
| **Экипировка (прокатный комплект)** | Шлем + подшлемник; может выдаваться напрокат. Подшлемник — предмет личной гигиены, при прокате выдаётся новым. |
| **Своя экипировка** | Клиент приезжает со своим шлемом и подшлемником; занимает место-карт в заезде, но **не** прокатный фонд. |
| **Прокат экипировки** | Выдача клубного комплекта (шлем + подшлемник); занимает место-карт **и** один прокатный комплект. |
| **Место-карт** | Одно место в заезде = один карт. Основной лимит слота (`free_seats`). |
| **Запись (бронь)** | Резерв одного или нескольких мест-картов на конкретный слот: число мест, своя/прокатная экипировка, статус. |
| **Отмена** | Снятие записи. Клиентом: ранняя (≥2 ч до старта) освобождает место-карт; поздняя (<2 ч) фиксируется без освобождения. Центром (организатором / по погоде): бронь переходит в статус «Отменён центром» с причиной, клиент получает push, повторная запись на этот слот запрещена. |
| **Отмена центром** | Отмена заезда организатором или из-за погоды (дождь/гололёд; выполняется в существующей инфраструктуре). На стороне клиента бронь сохраняется со статусом «Отменён центром» + причина; отправляется push-уведомление; повторная запись на отменённый слот недоступна. |
| **Инструктаж (брифинг)** | Предстартовый инструктаж от маршала; входит в слот заезда, отдельного шага записи не требует. |
| **Администратор / владелец** | Денис — управляет расписанием и маршалами через существующую инфраструктуру (вне скоупа клиентского приложения). |
| **MVP** | Минимально жизнеспособный продукт: набор функций к старту высокого сезона. |

### Технические термины (применяются в требованиях и ТЗ)

| Термин | Определение |
| :-- | :-- |
| **CTA (call-to-action)** | Основная кнопка действия на экране (напр. «Записаться», «Отменить запись»). В контексте слотов — кнопка перехода к бронированию. |
| **Empty state** | Состояние экрана при отсутствии данных (нет слотов / нет броней): заглушка с пояснением и подсказкой. |
| **Fallback** | Запасной режим при недоступности сервиса (напр. текстовое место сбора вместо карты при отказе Яндекс.Карт). Бронирование остаётся доступным. |
| **Offline-режим** | Работа при отсутствии сети: только просмотр кэша с пометкой «данные могли устареть»; мутации (бронь/отмена) запрещены. |
| **Idempotency-Key** | Клиентский ключ идемпотентности при создании брони: повтор запроса с тем же ключом и телом даёт идентичный ответ и не создаёт дубль. |
| **OTP (One-Time Password)** | Одноразовый код подтверждения входа по SMS; альтернатива паролю. |
