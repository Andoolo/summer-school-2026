# Промпты · Этап 2. Требования (BR/FR/NFR/US/UC)

> Цель: из брифа, ответов и домена получить структурированные требования с трассируемыми ID.
> Ключевая задача — не путать ФТ и НФТ, проработать альтернативные потоки в UC.

## Промпт 3 — бизнес- и функциональные требования

> **Промпт (отправлен ИИ):**
>
> Сформируй бизнес-требования (BR-NN) и функциональные требования (FR-NN) для клиентского
> приложения «Апекс». Источники — бриф, ответы заказчика, описание домена.
>
> Правила:
> - Стабильные ID (BR-1, FR-1 …), без переиспользования номеров; пропуски в нумерации допустимы
>   (следствие сужения скоупа) — не нормализуй их, чтобы не ломать трассу.
> - Приоритет по MoSCoW (Must/Should/Could/Won't).
> - Колонка «Источник» — откуда требование (бриф/ответ №/домен).
> - ФТ = «что система делает» (функции). НФТ — отдельно, сюда не клади.
> - Скоуп — только роль Клиент (моб. приложение + API). Функции маршала/владельца и расписание-CRUD
>   — существующая инфраструктура, не описывай.
>
> Доменная модель цены (картинг): price_total = price × seats_count + rental_price × rental_count,
> где price — за место-карт, rental_price — за комплект экипировки (шлем+подшлемник); карт всегда
> центра, своя экипировка бесплатна. Итог считает сервер, клиент не пересчитывает.

## Промпт 4 — нефункциональные требования

> **Промпт (отправлен ИИ):**
>
> Сформируй нефункциональные требования (NFR-NN) — «насколько хорошо» система работает, НЕ «что
> делает». Категории: удобство, платформа, производительность, надёжность/целостность, доступность,
> безопасность/приватность, уведомления, offline, a11y, интеграции.
>
> Каждое NFR — проверяемое, с приоритетом и источником. Различай: доступность (availability, %) vs
> доступность (a11y, WCAG). Дай измеримые метрики (p95 < 2.5 с, WCAG 2.1 AA, touch-target ≥44pt,
> retention 12 мес). Учти: нативное приложение iOS/Android, JWT access/refresh, SMS OTP с
> антифродом, offline-просмотр кэша, fallback Яндекс.Карт.

## Промпт 5 — user stories и use cases

> **Промпт (отправлен ИИ):**
>
> Сформируй user stories (US-NN) в формате «Как <роль>, я хочу <действие>, чтобы <ценность>» с
> критериями приёмки и трассировкой на FR. И use cases (UC-NN) с актёрами, целью, предусловиями,
> основным потоком, **альтернативными потоками** и **исключениями/ошибками**.
>
> ВАЖНО — альтернативные и исключительные потоки обязательны (ИИ любит их забывать). Для UC
> записи и отмены дай матрицу ошибок: код → HTTP → обязательные details → UX-реакция → retry.
>
> Все FR должны быть покрыты хотя бы одним US/UC (проверь обратную трассировку). Закрой сценарии:
> вход по SMS OTP, запись (себя+гости), отмена (правило 2 ч, ранняя/поздняя, отмена центром),
> фильтрация, профиль/удаление/logout.
>
> **Что сработало:** первичный прогон выявил (на ревью) висящие FR-43/45/46/47-49 и противоречие
> таймзоны — после правок все FR покрыты US+UC, матрица ошибок вынесена в отдельный артефакт.
