# Use cases / сценарии

> **Этап 2.** Сценарии использования. Обязательно прорабатываем **альтернативные потоки** —
> ИИ любит их забывать.
>
> **Скоуп: клиентское приложение и API для него.** Слоты, конфигурации трасс и маршалы поступают
> из существующего бэкенда через API (read-only).

## UC-1: Запись на заезд (себя и гостей)

- **Актёры:** Клиент
- **Предусловия:** Клиент авторизован; в расписании есть хотя бы один слот со свободными местами-картами.
- **Триггер:** Клиент хочет забронировать место на заезде.

> **Бизнес-решение по составу гостей (R-013).** По гостям собираем только **количество мест и
> выбор экипировки** (своя / прокатная). Имена, контакты, возраст и рост гостей в MVP **не
> собираются**; ответственность за гостей несёт клиент, оформивший бронь.
>
> **Бизнес-решение по идемпотентности (R-022).** Клиент **обязан** передавать `Idempotency-Key`
> при создании брони. Повтор той же операции (тот же ключ и то же тело запроса) даёт идентичный
> ответ и не создаёт дубль брони. Повтор с тем же ключом, но другим телом — ошибка.
>
> **Время и источник истины (R-021).** Время хранится и передаётся в UTC; бизнес-правила
> (правило 2 часов, окно выдачи) — в локальной зоне центра, отображение клиенту — в локальной зоне
> устройства клиента. Сервер — источник истины по времени и статусам; при расхождении клиентского
> прогноза и серверного ответа применяется серверный статус.

### Основной поток
1. Клиент открывает список слотов.
2. (Опц.) Применяет фильтры: дата/период, тип конфигурации трассы, наличие мест, маршал.
3. Открывает карточку слота и просматривает параметры (дата/время, конфигурация трассы, маршал,
   цена, свободно мест-картов, доступность прокатной экипировки, место сбора).
4. Указывает число мест (себя + до 2 гостей). По гостям указывается только количество (R-013).
5. Для каждого места выбирает вариант экипировки: своя / прокатная.
6. Подтверждает запись. Клиент формирует и передаёт `Idempotency-Key` для этой операции (R-022).
7. Система проверяет лимит мест `max_seats = min(free_seats, track_config.capacity_cap, 3)` (три
   фактора: свободные места-карты, потолок конфигурации, лимит 3 на бронь) и **отдельно** прокатный
   фонд экипировки `rental_count ≤ free_rental_kits`, создаёт запись, уменьшает счётчики свободных
   мест-картов/прокатных комплектов.
8. Система показывает подтверждение с ценой (оплата офлайн) и добавляет запись в «Мои бронирования».

### Альтернативные потоки
- **A1. Вся экипировка — своя.** На шаге 5 прокатный фонд не затрагивается; уменьшается только
  число мест-картов в заезде. (Карт всегда центра — «своя» относится только к экипировке.)
- **A2. Часть мест — с прокатом экипировки.** На шаге 7 проверяется и уменьшается прокатный фонд
  экипировки только на число «прокатных» мест.
- **A3. Фильтр не дал результатов.** На шаге 2 список пуст — система предлагает сбросить/изменить
  фильтры.

### Исключения / ошибки
- **E1. Не хватает мест-картов в заезде.** Запрошено больше, чем свободно мест-картов → запись
  отклоняется, показывается актуальное число свободных мест.
- **E2. Не хватает прокатной экипировки.** Прокатных мест запрошено больше, чем свободных
  комплектов → система предлагает уменьшить число прокатных мест или выбрать «своя экипировка».
- **E3. Гонка запросов / слот заполнился параллельно.** На шаге 7 места уже заняты другим клиентом
  → запись отклоняется без овербукинга и двойной брони (NFR-8), список обновляется.
- **E4. Сетевой сбой / неопределённый результат при подтверждении (R-020, R-022).** Запись не
  создаётся частично; при неопределённом результате клиент повторяет операцию с **тем же**
  `Idempotency-Key`, повтор не приводит к задвоению (NFR-9). Мутации (создание брони) офлайн
  запрещены — при отсутствии сети показывается понятное сообщение, кнопка подтверждения недоступна.
- **E5. Слот отменён или уже стартовал (R-023).** Слот к моменту подтверждения отменён центром или
  заезд начался → запись отклоняется с соответствующим кодом (`slot_cancelled` / `slot_started`).

### Матрица ошибок ключевых операций (R-023)

Полная таксономия кодов API вынесена в единый артефакт — [**error-matrix.md**](error-matrix.md)
(коды бронирования, авторизации, доступа, сетевые и серверные ошибки). Применяется ко всем
сценариям. Ниже — ошибки, релевантные именно UC-1:

| Код | HTTP | Обязательные `details` | UX-реакция | Retry |
| :-- | :-- | :-- | :-- | :-- |
| `slot_full` | 409 | `available_seats`, `available_rental_kits` | Показать актуальные свободные места-карты/прокатные комплекты, обновить карточку | Нет (изменить число мест) |
| `double_booking` | 409 | `booking_id` | Сообщить, что бронь на слот уже есть; перейти в «Мои бронирования» | Нет |
| `slot_cancelled` | 410 | `slot_id` | Сообщить об отмене слота центром, убрать CTA записи | Нет |
| `slot_started` | 422 | `slot_id`, `start_at` | Сообщить, что заезд начался/прошёл, запись недоступна | Нет |

> Коды авторизации (`invalid_code`, 401, 403), лимитов (429) и сетевые (5xx, offline) —
> см. [полную матрицу](error-matrix.md).

### Постусловия
- При успехе: создана запись клиента; счётчики слота и прокатного фонда экипировки уменьшены;
  запись видна в «Мои бронирования».
- При ошибке: состояние слота не изменилось.

## UC-2: Отмена записи

- **Актёры:** Клиент
- **Предусловия:** У клиента есть предстоящая запись; заезд ещё не стартовал.
- **Триггер:** Клиент решает отменить участие.

> **Бизнес-решение по объёму отмены (R-014).** Отмена выполняется **только целиком**: отменляется
> вся бронь со всеми местами-картами и прокатными комплектами экипировки. Частичная отмена
> (например, одного гостя) **не поддерживается**; при ранней отмене освобождаются все места-карты
> и прокатные комплекты брони.
>
> **Время и источник истины (R-021).** Время хранится и передаётся в UTC; бизнес-правило границы
> 2 часов считается в локальной зоне центра, отображение клиенту — в локальной зоне устройства
> клиента. Сервер — источник истины по времени и по статусу отмены. Граница политики: **ровно
> 2 часа до старта = ещё ранняя (бесплатная) отмена**. При расхождении клиентского прогноза
> (ранняя/поздняя) и серверного ответа применяется **серверный** статус.

### Основной поток
1. Клиент открывает «Мои бронирования» и выбирает предстоящую запись.
2. Нажимает «Отменить» (отмена всей брони целиком, R-014).
3. Сервер определяет время до старта (источник истины — серверное время, R-021).
4. **Ранняя отмена (≥2 ч до старта):** вся бронь помечается «отменена»; **все** забронированные
   места-карты и прокатные комплекты экипировки возвращаются в слот.
5. Система показывает подтверждение отмены.

### Альтернативные потоки
- **A1. Поздняя отмена (<2 ч до старта).** На шаге 4 запись помечается «поздняя отмена»; места-карты
  НЕ освобождаются; денежных штрафов нет; клиенту показывается пояснение политики 2 часов.
- **A2. Расхождение клиентского прогноза и сервера (R-021).** Клиент показал «ранняя отмена», а
  сервер вернул «поздняя» (или наоборот) → применяется и отображается серверный статус.

### Исключения / ошибки
- **E1. Заезд уже стартовал/прошёл (`slot_started`).** Кнопка отмены недоступна; запись нельзя
  отменить.
- **E2. Запись уже отменена (`already_cancelled`).** Повторная отмена не выполняется; показывается
  текущий статус.
- **E3. Отмена офлайн / неопределённый результат (R-020).** Мутация отмены офлайн запрещена — при
  отсутствии сети показывается понятное сообщение, кнопка недоступна; при неопределённом
  результате применяется единый Error/Retry, финальный статус берётся с сервера. Коды ошибок и
  UX-реакции — по матрице ошибок UC-1 (R-023).

### Постусловия
- Статус всей брони обновлён («отменена» / «поздняя отмена»).
- При ранней отмене все места-карты и прокатные комплекты экипировки снова доступны другим клиентам.

## UC-3: Просмотр и фильтрация списка слотов

- **Актёры:** Клиент
- **Предусловия:** Клиент авторизован.
- **Триггер:** Клиент хочет найти подходящий заезд.

### Основной поток
1. Клиент открывает список слотов. По умолчанию (`only_available=false`) показываются слоты на
   **ближайшие 7 дней** (дефолт API: `date_from = now`, `date_to = now + 7 дней`; больший период —
   явным фильтром дат, R-027), отсортированные по времени старта (по возрастанию).
2. Заполненные (`free_seats = 0`) и отменённые слоты отображаются в списке с пометкой «Мест нет» и
   неактивной (disabled) CTA записи (см. R-012).
3. (Опц.) Задаёт фильтры: дата/период, тип конфигурации трассы, наличие мест, маршал.
4. Система показывает отфильтрованный список с ключевыми параметрами каждого слота, сохраняя
   сортировку по времени старта.

### Альтернативные потоки
- **A1. Сброс фильтров.** Клиент очищает фильтры → возвращается дефолтная выдача (слоты на
  ближайшие 7 дней, дефолт без фильтров).
- **A2. Только свободные слоты.** Клиент включает фильтр наличия мест (`only_available=true`) →
  заполненные/отменённые слоты скрываются.
- **A3. Семантика комбинирования фильтров (R-026).** Внутри одной группы значения комбинируются по
  «ИЛИ» (`route_type`, `marshal_id` — массивы), между разными группами — по «И». Границы периода
  дат включительные; ввод и трактовка дат — в локальной зоне (дате) клиента. Активные фильтры отображаются
  клиенту.
- **A4. Пустой справочник маршалов.** Если список маршалов пуст, фильтр по маршалу скрывается.

### Исключения / ошибки
- **E1. Нет слотов под условия.** Показывается пустое состояние с подсказкой изменить/сбросить
  фильтры.
- **E2. Нет расписания вовсе.** В горизонте выдачи нет ни одного предстоящего слота → показывается
  пустое состояние «Заездов пока нет».
- **E3. Просмотр офлайн (R-020).** При отсутствии сети показывается ранее загруженный кэш списка с
  пометкой «данные могли устареть»; единый Error/Retry для повторной загрузки.

### Постусловия
- Клиент видит актуальный (или помеченный как устаревший) список предстоящих слотов; данные
  расписания не изменяются.

## UC-4: Вход по SMS OTP

- **Актёры:** Клиент
- **Предусловия:** Клиент не авторизован (или сессия истекла).
- **Триггер:** Клиент запускает приложение или нажимает «Войти».

> **Антифрод (NFR-19).** Отправка OTP ограничена rate-limit'ами (~1 запрос/30–60 с, ~5/час на
> номер/устройство); число попыток ввода ≤5 до временной блокировки; код имеет конечный TTL.

### Основной поток
1. Клиент вводит номер телефона (нормализация/валидация формата).
2. Клиент нажимает «Получить код» → приложение запрашивает OTP у бэкенда.
3. Бэкенд отправляет одноразовый код в SMS.
4. Клиент вводит код из SMS.
5. Бэкенд проверяет код, выдаёт пару токенов (access/refresh, NFR-18); приложение сохраняет их в
   защищённом хранилище (Keychain/Keystore).
6. Если телефон новый — клиент вводит имя (см. FR-1, лёгкая регистрация).
7. Клиент попадает на список слотов.

### Альтернативные потоки
- **A1. Существующий клиент.** На шаге 6 имя не запрашивается — клиент сразу авторизован.
- **A2. Смена телефона в профиле.** Тот же поток OTP применяется при смене телефона в профиле
  (FR-47), с подтверждением нового номера кодом.

### Исключения / ошибки
- **E1. Неверный код (`invalid_code`).** Поле OTP остаётся активным; показывается «неверный код»;
  после исчерпания попыток (≤5) — временная блокировка с указанием времени до повтора.
- **E2. Лимит запросов кода (429, `retry_after`).** Слишком частый запрос кода → отложенный повтор
  с указанием времени.
- **E3. Код просрочен / недоставлен.** TTL истёк или SMS не пришло → предложение «Отправить код
  повторно» (с учётом E2).
- **E4. Сетевая ошибка.** Единый Error/Retry; номер маскируется в UI и логах (NFR-20).

### Постусловия
- При успехе: создана/продлена сессия клиента; токены в защищённом хранилище; доступ к
  авторизованной зоне.
- При ошибке: сессия не создаётся.

## UC-5: Управление профилем и аккаунтом

- **Актёры:** Клиент
- **Предусловия:** Клиент авторизован.
- **Триггер:** Клиент открывает «Профиль».

> **Удаление аккаунта и ПДн (R-009, NFR-20).** При удалении активные брони аннулируются и
> освобождают места-карты и прокатные комплекты; прошедшие брони **анонимизируются** (без привязки
> к ПДн) и сохраняются для учёта; ПДн клиента анонимизируются, номер телефона освобождается для
> повторной регистрации.

### Основной поток (просмотр/редактирование профиля)
1. Клиент открывает профиль: видит имя и телефон (маскированный в UI).
2. При желании редактирует имя → сохраняет.
3. При смене телефона — повторно проходит SMS OTP на новый номер (см. UC-4 A2).

### Альтернативные потоки
- **A1. Выход из аккаунта (logout, FR-49).** Клиент нажимает «Выйти» → токены очищаются из
  защищённого хранилища → переход на экран входа (UC-4).
- **A2. Удаление аккаунта (FR-48).** Клиент нажимает «Удалить аккаунт» → подтверждение
  (деструктивное действие) → бэкенд аннулирует активные брони и освобождает места-карты/прокатные
  комплекты, прошедшие брони анонимизируются, ПДн клиента анонимизируются → переход на вход.

### Исключения / ошибки
- **E1. Сетевая ошибка при сохранении.** Единый Error/Retry; локальные правки не применяются до
  подтверждения сервером.
- **E2. Удаление аккаунта при офлайне.** Мутация удаления офлайн запрещена (NFR-24) — понятное
  сообщение, кнопка недоступна.

### Постусловия
- При редактировании: профиль обновлён; телефон (при смене) подтверждён OTP.
- При выходе: сессия закрыта, токены удалены.
- При удалении: аккаунт обезличен, активные брони аннулированы, ресурсы освобождены.
