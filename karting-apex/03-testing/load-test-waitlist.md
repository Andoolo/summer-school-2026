# Нагрузочный тест листа ожидания (k6)

Проверка того, что лист ожидания и брони остаются корректными при одновременных записях,
отменах и раздаче мест. Сценарий — [`backend/k6/waitlist_300_vu.js`](../backend/k6/waitlist_300_vu.js),
проверки корректности — [`backend/k6/waitlist_invariants.sql`](../backend/k6/waitlist_invariants.sql),
данные — `go run ./cmd/k6seed`.

> Прогон на **локальном стенде**, не на проде: Docker Desktop на Windows, 20 CPU, PostgreSQL 16
> в контейнере, API в контейнере, имитатор Telegram Bot API. k6 2.0.0 в Docker. 14.09.2026.

## Что моделирует сценарий

Три заезда по 8 мест, все места заняты. 224 виртуальных пользователя в течение 3 минут:

| Роль | Кто | Что делает |
|---|---|---|
| **Держатели** | 24 пользователя, по 8 на заезд | отменяют бронь и сразу пытаются забронировать снова — конкурируют за место с теми, кому оно предложено |
| **Ждущие** | 200 пользователей | встают в очередь, следят за статусом, бронируют по предложению, выходят из очереди (5% шагов), иногда отменяют бронь |

Рассыльщик работает как на проде: раздаёт места по сигналу после каждой брони, отмены и
записи в очередь, и раз в минуту. Сообщения уходят в имитатор Telegram.

Такой сценарий жёстче жизни: все 224 пользователя бьются за строки всего трёх заездов.

## Откуда пики задержки

Медиана около 1 мс, но максимум доходил до 8,5 с, и от прогона к прогону p95 менялся
в 20 раз. Разобрано по снимкам `pg_stat_activity` раз в 200 мс во время нагрузки:

- **Пул соединений API упирается в потолок** — 20 из 20 (по умолчанию pgx: число CPU).
- **Транзакции ждут записи журнала при фиксации** (`commit` в ожидании `IO`/`LWLock`) —
  медленный диск PostgreSQL внутри Docker Desktop на Windows. Разброс между прогонами
  объясняется им же.
- **Очередь на блокировку строки заезда** (`SELECT … FOR UPDATE`): вход в очередь и бронь
  одного заезда выполняются по очереди. Это защита от перепродажи мест, а в сценарии все
  пользователи бьются за три строки.

Когда диск тормозит, фиксации затягиваются, пул заканчивается, и даже простые чтения ждут
свободное соединение. Ошибок это не вызывает, корректность не нарушается.

## Повторный замер 24.09: блокировки, пул, диск

Проверены все три гипотезы из разбора выше. Тот же сценарий, по 2 минуты на прогон, у каждого
запроса метка `name`: сводка k6 показывает время по эндпоинтам. Во всех прогонах 0 ошибок и
0 нарушений инвариантов.

| Прогон | p95, все | p95, вход в очередь | p95, бронь | p95, отмена | Максимум |
|---|---|---|---|---|---|
| Вход в очередь с `FOR UPDATE` (прогоны 1 и 2) | 30 / 43 мс | 267 / 268 мс | 74 / 179 мс | 124 / 290 мс | 2,1 / 3,5 с |
| Вход в очередь с `FOR SHARE` (прогоны 1 и 2) | 294 / 65 мс | 447 / 103 мс | 412 / 142 мс | 1 188 / 309 мс | 2,1 / 2,5 с |
| `FOR SHARE`, пул 40 соединений вместо 20 | 72 мс | 136 мс | 140 мс | 182 мс | 2,3 с |
| `FOR SHARE`, пул 20, **`synchronous_commit = off`** | **2,6 мс** | **80 мс** | **3,6 мс** | **3,7 мс** | **0,9 с** |

**Выводы:**

- **Хвосты задержки даёт диск среды, а не код.** Без ожидания записи журнала при фиксации
  (`synchronous_commit = off`, только на локальном стенде для диагностики) p95 брони и отмены
  падает с 70–1 200 мс до 4 мс, а максимум — с 2–3,5 с до 0,9 с. Вход в очередь остаётся
  медленнее (p95 80 мс): он ждёт, пока бронь того же заезда отпустит строку, — так очередь
  и не расходится с бронями. На проде база в Neon, и фиксация там не ждёт медленный диск
  Docker Desktop.
- **Пул не узкое место.** С 40 соединениями вместо 20 результат в пределах разброса между
  прогонами одной и той же сборки.
- **`FOR SHARE` не дал измеримого выигрыша:** разброс прогонов больше эффекта. Его оставили:
  с бронями он согласован так же, как `FOR UPDATE`, а входы разных людей больше не ждут друг
  друга (`TestWaitlistJoinsDoNotWaitForEachOther`). Важнее другая правка того же места —
  блокировка на человека. Она закрыла найденную тестом гонку: два одновременных входа одного
  человека в разные заезды проходили оба и превышали лимит в 5 очередей
  (`TestWaitlistLimitHoldsForConcurrentJoins`; на старом коде тест падает 3 раза из 3).
- **Попутно найдена ошибка запуска:** `pool_max_conns` в `DATABASE_URL` ронял сервис при старте.
  Миграции подключались мимо пула и отправляли параметр серверу, а Postgres отвечал
  `unrecognized configuration parameter`. Исправлено: миграции и сид разбирают строку так же,
  как пул (`TestPoolParamsInDatabaseURL`). Теперь размер пула задаётся прямо в строке,
  например `...&pool_max_conns=10`.

## Как запустить

```bash
cd karting-apex/backend
# стенд: API с TELEGRAM_BOT_TOKEN и TELEGRAM_API_BASE на имитатор Bot API, RATE_LIMIT=off
go run ./cmd/k6seed
k6 run k6/waitlist_300_vu.js                  # или: make k6-waitlist
# через минуту, после последнего прохода рассыльщика:
psql "$DATABASE_URL" -f k6/waitlist_invariants.sql   # или: make k6-waitlist-check
```

> Лимиты запросов по IP на время прогона выключены: k6 шлёт всё с одного адреса.
> Не запускать против прода: сидер переписывает данные k6-пользователей и создаёт заезды.
