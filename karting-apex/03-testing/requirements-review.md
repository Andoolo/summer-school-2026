# Столп 1 · Ревью требований на тестопригодность (ИИ + сабагенты)

> **Цель:** проверить требования «Апекса» не на «правильность», а на **тестопригодность** — можно ли
> по ним написать полные однозначные тест-кейсы (позитив/негатив/edge). Это вход для Столпа 2.
>
> **Метод (по методологии лекции Блока 3):** два параллельных read-only сабагента с разными зонами,
> затем консолидация отчётов с пометкой пересечений/различий.
> - **Агент A** — требования: `01-analysis/2-requirements/` (BR/FR/NFR, US, UC).
> - **Агент B** — экраны + контракт: `01-analysis/5-mobile-app-spec/` (SCR/BS/LOGIC) + `01-analysis/api/`.
>
> **Инструменты:** Claude Code + 2 сабагента (general-purpose), read-only.

## Общий вывод

Пакет спецификаций **очень зрелый**. Слой `5-mobile-app-spec` (LOGIC-001…008, SCR-001…007) даёт
Gherkin-AC с позитивом/негативом/edge и матрицами ошибок — по ним тест-кейсы пишутся почти 1:1.
Блокеры тестируемости сконцентрированы **на верхнем слое** (FR/NFR — формулировки без порогов,
рассинхрон со спекой) и в нескольких **рассогласованиях спек ↔ API-контракт**.

**Пересечение агентов (оба независимо):** проблемы вокруг **списков + пагинации + сортировки**
(SCR-002/SCR-005) и «мягкие» NFR/пороги. Оба отметили высокую зрелость app-spec слоя.

> **Связь с Блоком 2:** CRITICAL про сортировку броней (ниже, C2) — та самая зона, что мы уже
> исправили в **B2** (двунаправленный `ORDER BY` на сервере). Наш фикс закрывает поведение, но
> **текстовое противоречие в спеке остаётся** — его надо развести отдельно. См. `02-development/tasks/B2-*.md`.

## CRITICAL

### C1 · FR-9 vs US-2 — дефолтное окно выдачи слотов противоречиво `[Агент A]`
- **Где:** `2-requirements/functional-requirements.md` FR-9 (и UC-3, LOGIC-005) vs `user-stories.md` US-2 (AC).
- **Конфликт:** FR-9 — по умолчанию слоты на **ближайшие 7 дней** (`date_to = now+7`). US-2 AC — «показываются **ВСЕ** предстоящие слоты».
- **Мешает тесту:** «Дано слоты на +3д и +10д при дефолтной выдаче видно…» — по FR-9 +10д НЕ в списке, по US-2 — в списке. Оракул неопределён.
- **Уточнить:** привести US-2 к FR-9 («7 дней»); `only_available` — это ось наличия мест, не окно дат.

### C2 · SCR-005 сортировка + пагинация: спека vs API-контракт `[Агент B]` · ⚠️ связано с B2
- **Где:** `api/bookings/api.yaml` `listBookings` (сорт по `start_at` **DESC**) vs `SCR-005-my-bookings.md` §Обзор (стр. 49) и §Клиентская группировка (стр. 175-177: предстоящие клиент пересортирует **ASC**).
- **Конфликт:** сервер отдаёт DESC + пагинация (`limit`/`offset`) → ближайшие предстоящие оказываются на **последних** страницах и «ближайшая сверху» может не догрузиться. Совместное поведение «серверные страницы ↔ клиентская пересортировка накопленного набора» не специфицировано.
- **Мешает тесту:** нельзя однозначно написать кейс на порядок при пагинации.
- **Статус:** на сервере закрыто нашим **B2** (двунаправленный порядок: upcoming ASC, past DESC). **Но спеку надо привести в соответствие** (сейчас `api.yaml` всё ещё пишет «DESC»).

## MEDIUM

- **M1 `[B]` OTP-код в теле ответа (demo)** — `RequestCodeResponse.code`; SCR не оговаривают среду → негативные OTP-кейсы недетерминированы. *(Связь с B1: в prod код не отдаётся — среду тестирования надо зафиксировать.)*
- **M2 `[B]` дефолт `limit`**: SCR-002 «грузится целиком», API default `limit=20` без пагинации на экране → при >20 слотов потеря данных. Задать `limit=100`/поведение при >100.
- **M3 `[A]` NFR-1/2/3** — качественные; измеримость частично в NFR-25; снять «(предположение)» с NFR-2 (SCR-004 трактует ≤3 жёстко).
- **M4 `[A]` нормализация телефона**: E.164 задан, правило преобразования локального ввода (`8…`→`+7…`) — нет.
- **M5 `[A]` retention 12 мес (NFR-20) vs анонимизация при удалении (FR-48)** — два триггера не разведены во времени.
- **M6 `[A]` пагинация**: размер страницы не зафиксирован (рантайм-конфиг) → точный кейс догрузки не написать; границы (пустая след. страница, вставка во время PTR) без AC. *(Пересекается с H10.)*
- **M7 `[B]` полу-регистрация**: refresh упал на шаге «Имя» (verify прошёл, имя пусто) → повторный вход `is_new=false`, шаг имени пропущен, юзер без имени. Граничный кейс без AC.
- **M8 `[B]` rental_count ≤ seats_count** не выражен в JSON-схеме (только `maximum:3`) → контрактный/фаззинг-тест API не знает ожидаемого ответа на `rental=3,seats=1`.
- **M9 `[A]` reminder_hours / push** — доставка «вне скоупа» → нетестируемо на клиенте; US-12/FR-33 без клиентского AC. Пометить границу явно.
