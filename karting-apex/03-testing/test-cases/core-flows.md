# Столп 2 · Детальные тест-кейсы (ядро + регресс Блока 2)

> Формат: `TC-<область>-<n>` · **P** приоритет · **Тип** (C/S) · шаги → ожидание · привязка к AC/требованию.
> Теги: `@regress:Xn` — регресс на нашу фичу/баг; `@needs-clarification` — оракул зависит от нерешённого требования (см. `requirements-review.md`).
> Машиночитаемая версия части кейсов — в [`test-cases.yaml`](test-cases.yaml).

## AUTH — авторизация по OTP + сессия (SCR-001, SCR-007, LOGIC-001) · регресс B1, F3

### TC-AUTH-01 · Запрос кода по валидному телефону · P0 · C
- **Дано:** гость на экране входа.
- **Шаги:** ввести `+79991112233` → «Получить код».
- **Ожидание:** 200; ответ содержит `ttl_seconds`, `resend_after_seconds`; экран переходит к вводу кода; запускается resend-таймер.
- **AC:** LOGIC-001 шаг 1; FR-43.

### TC-AUTH-02 · OTP-код НЕ возвращается в prod, возвращается в dev · P0 · S · `@regress:B1`
- **Дано:** два окружения API (`APP_ENV=production` и `development`).
- **Шаги:** `POST /auth/request-code` в каждом.
- **Ожидание:** dev — тело содержит `code`; production — **поле `code` отсутствует** (утечки нет). NFR-19/NFR-20.
- **Проверено в Блоке 2:** curl dev/prod (см. `02-development/tasks/B1-otp-code-leak.md`).

### TC-AUTH-03 · Невалидный телефон · P1 · C
- **Шаги:** ввести `+7999` / `abc` / пустой → «Получить код».
- **Ожидание:** клиентская валидация (E.164 `^\+[1-9]\d{1,14}$`) блокирует отправку либо 400 `bad_request`.
- **AC:** LOGIC-001; `@needs-clarification` (нормализация локального ввода `8…`→`+7…`, M4).

### TC-AUTH-04 · Resend-таймер / повторный запрос до истечения · P1 · S
- **Шаги:** запросить код, сразу запросить ещё раз (в пределах `resend_after`).
- **Ожидание:** 429 `too_many_requests` (если предыдущий OTP не потреблён); кнопка «Получить код» неактивна до конца таймера.
- **AC:** LOGIC-001; примечание: после успешного verify (OTP потреблён) повторный запрос разрешён.

### TC-AUTH-05 · Verify: неверный код / истёкший / превышение попыток · P0 · C
- **Шаги:** ввести неверный код ×N; ввести истёкший код (после TTL).
- **Ожидание:** 400 `invalid_code` «Неверный или истёкший код»; после `maxAttempts=5` — 429; истёкший → invalid_code.
- **AC:** LOGIC-001; matrix UC-1.

### TC-AUTH-06 · Verify успешный → пара токенов · P0 · C · `@regress:F3`
- **Шаги:** ввести корректный код.
- **Ожидание:** 200; тело содержит `token` (совместимость) **и** `tokens{access_token, refresh_token, token_type:"Bearer", expires_in}`; `client`, `is_new`.
- **Проверено в Блоке 2:** live-флоу (`F3-auth-refresh.md`).

### TC-AUTH-07 · Обновление сессии через /auth/refresh (ротация) · P0 · S · `@regress:F3`
- **Дано:** валидная пара токенов.
- **Шаги:** `POST /auth/refresh {refresh_token}` → получить новую пару; повторно предъявить **старый** refresh.
- **Ожидание:** первый вызов 200 (новая пара); повторный старый refresh → **401** (ротация/reuse-защита, H1).
- **Проверено:** live (reuse → 401).

### TC-AUTH-08 · Logout гасит только текущую сессию (мульти-девайс) · P0 · S · `@regress:F3`
- **Дано:** один клиент, две сессии (устройства A и B).
- **Шаги:** `logout` токеном A → refresh A; refresh B.
- **Ожидание:** logout A → 204; refresh A → **401**; refresh B → **200** (другое устройство не затронуто, H2).
- **Проверено:** live (refreshA 401, refreshB 200).

### TC-AUTH-09 · 401 на защищённом запросе → refresh → retry → при неудаче logout · P1 · S
- **Шаги:** протухший access → защищённый запрос → 401 → авто-refresh → повтор исходного; если refresh не помог — оба токена стёрты, возврат в НЗ.
- **Ожидание:** прозрачное продление; при провале — выход. `@needs-clarification` (полу-регистрация, M7).

## SLOTS + карта — список и карточка (SCR-002, SCR-003, BS-004) · регресс F1, F2

### TC-SLOT-01 · Загрузка списка слотов · P0 · C
- **Шаги:** открыть «Заезды».
- **Ожидание:** Loading (скелетоны) → Content; каждый слот: дата/время, трасса, маршал, места, цена; `free_seats=0` → «мест нет».
- **AC:** SCR-002; LOGIC-002.

### TC-SLOT-02 · Пустое / ошибка / PTR · P1 · S
- **Шаги:** нет слотов; ошибка сети; pull-to-refresh (успех и ошибка).
- **Ожидание:** Empty-заглушка; Error + «Обновить»; PTR-успех — контент без снека; PTR-ошибка — контент сохранён + снек.
- **AC:** SCR-002; LOGIC-008.

### TC-SLOT-03 · Фильтры (тип трассы, только доступные) · P1 · C
- **Шаги:** применить `route_type=novice/experienced`, `only_available=true`.
- **Ожидание:** выдача сужается корректно; `only_available` оставляет `free_seats>0`.
- **AC:** LOGIC-005; `@needs-clarification` (окно 7 дней, C1; дефолт `limit`, M2).

### TC-SLOT-04 · Карточка слота отдаёт geometry трассы · P0 · C · `@regress:F1`
- **Шаги:** `GET /slots` и `GET /slots/{id}` с токеном.
- **Ожидание:** `route.geometry` присутствует (массив `[[lat,lng],…]`); совпадает с данными трассы.
- **Проверено в Блоке 2:** curl list+detail (`F1-route-geometry-slots.md`).

### TC-SLOT-05 · Карта рисует реальный трасса по geometry · P0 · C · `@regress:F2`
- **Шаги:** открыть карточку слота с непустой geometry.
- **Ожидание:** на карте — ломаная по реальным координатам (для сид-трассы «Городское кольцо» — контур трассы по 6 точкам), пин в старте; форма соответствует координатам (север сверху, без искажения).
- **Проверено:** wasmJs BUILD SUCCESSFUL; визуально в браузере.

### TC-SLOT-06 · geometry = null → декоративный fallback · P2 · C · `@regress:F2`
- **Шаги:** слот без geometry.
- **Ожидание:** экран не падает; показывается декоративная заглушка-линия; поле geometry опускается в ответе.
- **AC:** BS-004 (Empty `geometry=null`).

## BOOKING — оформление и отмена (SCR-004, SCR-006, BS-003, LOGIC-002/003/004)

### TC-BOOK-01 · Успешная запись · P0 · C
- **Шаги:** slot с местами → `seats_count=2, rental_count=1` → подтвердить.
- **Ожидание:** 201; бронь `active`; `price_total` = серверный расчёт; уменьшены `free_seats`/`free_rental_boards`.
- **AC:** SCR-004; LOGIC-002/003.

### TC-BOOK-02 · Границы мест и проката · P1 · C
- **Шаги:** `seats_count` = 0/1/3/4; `rental_count` = -1/0/seats/seats+1.
- **Ожидание:** валидно только `seats ∈ 1..3` и `rental ∈ 0..seats`; иначе 400/блок UI.
- **AC:** data-model инварианты; `@needs-clarification` (M8 — `rental≤seats` не в JSON-схеме).

### TC-BOOK-03 · Идемпотентность повторной записи · P0 · S
- **Шаги:** `createBooking` с `Idempotency-Key` → повтор того же запроса с тем же ключом.
- **Ожидание:** второй ответ — та же бронь (не создаётся дубль); конфликт ключа с другим телом → 409 `idempotency_key_conflict`.
- **AC:** SCR-004 E4; AGENTS.md инвариант.

### TC-BOOK-04 · Конкурентная запись без овербукинга · P0 · S · (NFR-8/NFR-22)
- **Дано:** slot с `free_seats=1`.
- **Шаги:** N параллельных `createBooking` на это место.
- **Ожидание:** ровно 1 успех (201), остальные — 409 `slot_full`; счётчики консистентны; **0 дублей**.
- **AC:** NFR-8; проверяется через существующий интеграционный тест `TestCreateBookingConcurrencyDoesNotOverbook`.

### TC-BOOK-05 · Ошибки записи (матрица 409/422/410) · P1 · C
- **Шаги:** запись на полный слот; двойная запись; на отменённый клубом; после старта.
- **Ожидание:** 409 `slot_full` / 409 `double_booking` / 410 `slot_cancelled` / 422 `slot_started`.
- **AC:** UC-1; `@needs-clarification` (H9 — различение мест/проката).

### TC-BOOK-06 · Ранняя отмена (≥2ч) освобождает места · P0 · S
- **Шаги:** отменить бронь при `start_at - now ≥ 2ч` (и ровно = 2ч).
- **Ожидание:** 200, статус `cancelled`; `free_seats`/`free_rental_boards` возвращены; ровно 2ч = ранняя.
- **AC:** LOGIC-004; проверяется тестом `TestCancelBookingEarlyLateAndAfterStart`.

### TC-BOOK-07 · Поздняя отмена (<2ч) — late_cancel, места НЕ освобождаются · P0 · S
- **Шаги:** отменить при `start_at - now < 2ч`.
- **Ожидание:** 200, статус `late_cancel`; места/экипировки НЕ возвращены.
- **AC:** LOGIC-004.

### TC-BOOK-08 · Отмена: already_cancelled / после старта · P1 · C
- **Шаги:** повторная отмена; отмена после `start_at`.
- **Ожидание:** 409 `already_cancelled`; 422 `slot_started`.
- **AC:** LOGIC-004; тест `TestCancelBookingEarlyLateAndAfterStart`.

## MY BOOKINGS — мои записи (SCR-005) · регресс B2

### TC-MYB-01 · Группировка предстоящие/прошедшие · P0 · C
- **Шаги:** брони с разными датами/статусами → открыть «Мои записи».
- **Ожидание:** разделение на «Предстоящие»/«Прошедшие»; по умолчанию — Предстоящие.
- **AC:** SCR-005 AC-001/002/003.

### TC-MYB-02 · Порядок сортировки (ближайшая предстоящая сверху, свежая прошедшая сверху) · P0 · S · `@regress:B2`
- **Дано:** брони на now+1д, now+10д, now−1д, now−10д.
- **Шаги:** `GET /bookings`.
- **Ожидание:** предстоящие по возрастанию (`+1д` перед `+10д`, AC-002); прошедшие по убыванию (`−1д` перед `−10д`, AC-003); при пагинации релевантные — первыми.
- **Проверено в Блоке 2:** SQL-прогон OLD/GLM/принятый (`B2-booking-list-sort-order.md`); `@needs-clarification` (C2 — спека `api.yaml` пишет DESC).

### TC-MYB-03 · Отменённая бронь с будущим стартом → «Прошедшие» · P1 · C
- **Шаги:** бронь `cancelled`/`late_cancel`/`club_cancelled` с `start_at` в будущем.
- **Ожидание:** попадает в «Прошедшие» с бейджем; для `club_cancelled` — текст `cancellation_reason`.
- **AC:** SCR-005 AC-E01/AC-009; `@needs-clarification` (H7 — источник `club_cancelled`).

### TC-MYB-04 · Только свои брони (NFR-12) · P0 · S
- **Шаги:** клиент A запрашивает `/bookings`; пытается `GET /bookings/{id чужой брони}`.
- **Ожидание:** видит только свои; чужая бронь → 403 `forbidden`.
- **AC:** NFR-12; тест `TestListAndGetBookings` (forbidden-ветка).

### TC-MYB-05 · Пагинация (ленивая догрузка) · P2 · S
- **Шаги:** >1 страницы броней → скролл к концу.
- **Ожидание:** догрузка следующей страницы (`offset += limit`); группировка/сортировка пересчитываются на накопленном наборе.
- **AC:** SCR-005 AC-008; `@needs-clarification` (H10 — `PaginationMeta` без `has_next`; дубли при вставке во время PTR).
