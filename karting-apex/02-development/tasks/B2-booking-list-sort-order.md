# B2 · Баг: сортировка списка броней ломает пагинацию (ближайшая запись теряется)

> **Тип:** баг (логика/UX) · **Слой:** backend (storage) · **Сложность:** низкая · **Статус:** ✅ исправлено

## Симптом

`GET /bookings` (`listBookings`) возвращал записи с `ORDER BY s.start_at DESC`.
С пагинацией (`limit`/`offset`, R-025) это значит: **первая страница набивается самыми ДАЛЬНИМИ
будущими бронями**, а ближайшая предстоящая запись — та, что по AC-002 должна быть «сверху» —
оказывается ниже и при малом `limit` не попадает в первый экран ленивой загрузки.

Пример (клиент с бронями на `+1д`, `+10д`, `−1д`, `−10д` от текущего момента), `limit=1`:
первой страницей приходит `+10д` (самая дальняя), а не `+1д` (ближайшая, которую клиент и ищет).

На экране «Мои записи» ([SCR-005](../../01-analysis/5-mobile-app-spec/SCR-005-my-bookings.md)),
контекст «берег, спешка» — клиенту нужно **с одного взгляда** увидеть ближайшую заезд.
Плоский `DESC` этому противоречит.

## Причина / root cause

`backend/internal/storage/postgres/bookings.go`, `BookingRepository.List`:

```go
ORDER BY s.start_at DESC, b.created_at DESC
```

Плоский `DESC` по `start_at` не разделяет предстоящие и прошедшие и ставит дальние будущие брони
первыми. Требования же (SCR-005 §«Клиентская группировка», критерии AC-002/AC-003) описывают
**два разных направления** сортировки внутри групп:

- **Предстоящие** — по **возрастанию** `start_at` (ближайшая сверху).
- **Прошедшие** — по **убыванию** `start_at` (свежие сверху).

Финальную группировку делает клиент, но при ленивой пагинации он видит только уже загруженные
страницы — поэтому сервер обязан выдавать релевантные строки (ближайшие предстоящие и свежие
прошедшие) **первыми**, иначе на первые страницы они не попадут.

## Требования

- [SCR-005 «Мои записи»](../../01-analysis/5-mobile-app-spec/SCR-005-my-bookings.md), секция
  «Клиентская группировка» и критерии приёмки:
  - **AC-002** (P0): предстоящая (`active` + `start_at > now`) — в группе «Предстоящие», ближайшая сверху.
  - **AC-003** (P0): прошедшие отсортированы по **убыванию** даты старта (свежие сверху).
  - **AC-008** (P1): при пагинации группировка/сортировка пересчитываются на накопленном наборе —
    значит на первых страницах должны быть самые релевантные записи.
- FR-35a, US-9.

## Реализация

Файл: `backend/internal/storage/postgres/bookings.go` — `ORDER BY` в `List` переписан на
**двунаправленный**:

```sql
ORDER BY
  (CASE WHEN s.start_at >= NOW() THEN 0 ELSE 1 END),      -- предстоящие раньше прошедших
  CASE WHEN s.start_at >= NOW() THEN s.start_at END ASC,   -- предстоящие: ближайшая первой (AC-002)
  s.start_at DESC,                                         -- прошедшие: свежие первыми (AC-003)
  b.created_at DESC                                        -- стабильный тай-брейкер
```

Как это работает:
- **Ключ 1** делит выдачу на блок предстоящих (`0`) и блок прошедших (`1`).
- **Ключ 2** активен только для предстоящих (для прошедших `= NULL`, все равны) → предстоящие
  сортируются `start_at ASC` (ближайшая первой) — AC-002.
- **Ключ 3** для прошедших (у них ключ 2 `= NULL`) даёт `start_at DESC` (свежие первыми) — AC-003.
  Для предстоящих ключ 3 — лишь тай-брейкер после уникального ключа 2.

> **Примечание по ревью (Claude Code).** Первичный фикс (ZCode/GLM) был
> `ORDER BY (CASE ... 0 ELSE 1 END), s.start_at ASC, b.created_at DESC` — он корректно выносит
> ближайшие предстоящие вперёд (AC-002), но прошедшие при этом идут по **возрастанию** (старые
> первыми), что нарушает **AC-003** (свежие первыми) и повторяет ту же пагинационную хрупкость уже
> для вкладки «Прошедшие». Двунаправленный вариант закрывает оба P0-критерия одновременно — см.
> сравнение в разделе «Проверка».

## Промпты ИИ

> **Промпт (диагностика):** На SCR-005 ближайшая предстоящая бронь должна быть сверху (AC-002),
> прошедшие — свежие сверху (AC-003). Список пагинируется (limit/offset). Текущий
> `ORDER BY s.start_at DESC` кладёт дальние будущие брони на первую страницу. Как переписать
> сортировку, чтобы и предстоящие (ASC), и прошедшие (DESC) выдавались релевантными первыми в
> одном запросе, совместимо с пагинацией?
>
> **Действие по подсказке:** двунаправленный `ORDER BY`: сперва группа (upcoming/past), затем для
> upcoming `start_at ASC`, для past `start_at DESC`, стабильный тай-брейк `created_at DESC`.

## Проверка (ручная)

Смешанный набор броней одного клиента: слоты на `now+1д`, `now+10д`, `now−1д`, `now−10д`.
Сравнение трёх вариантов `ORDER BY` на живой БД (Postgres 16 в Docker, `psql`, транзакция с
`ROLLBACK` — данные не остаются). Текущая дата прогона — `2026-07-04`.

```text

 d0000010-0000-0000-0000-000000000010 | 2026-06-24 | past       ← СТАРАЯ прошедшая первой ✗ (нарушает AC-003)

                  id                  |  start_at  |   grp
--------------------------------------+------------+----------
 c0000001-0000-0000-0000-000000000001 | 2026-07-05 | upcoming   ← ближайшая первой ✅ (AC-002)
```

Итог принятого варианта: `07-05, 07-14, 07-03, 06-24` — в обеих группах релевантные записи идут
первыми, что корректно и для пагинации (первая страница = ближайшая предстоящая + свежая прошедшая).
✅ AC-002 и AC-003 выполнены одновременно.

## Правки по ревью (M3)

Граница «предстоящие/прошедшие» переведена с SQL `NOW()` на параметр `$now` из инъектируемых часов
(`BookingRepository.now`, дефолт `time.Now`) — сортировка стала тестируемой и с явным моментом
времени. Полная стабильность порядка **между страницами** пагинации (когда бронь пересекает границу
`now` между запросами) требует клиентского anchor-времени или курсорной пагинации — отмечено как
follow-up, вне текущего скоупа. См. `02-development/REVIEW-block2.md`.
